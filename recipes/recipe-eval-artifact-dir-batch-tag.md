model: 多模型实验：结果 JSON 按 AB_TAG 分文件，代码产物目录没分
problem: 同一台机器上先后跑两个模型做交叉验证。结果文件用 AB_TAG 分成了 results.zhipu.json 与 results.deepseek.json，看起来已经隔离好了；但模型生成的代码文件写在共用的
  runs/ 目录里，文件名只含「组_任务_第几次_第几轮」，不含模型标识。第二轮跑完后，第一轮的代码被同名文件全部覆盖。等审计时想复盘「第一个模型到底写了什么」，证据已经没有了。
dead_ends:
- attempt: 只给结果文件加模型后缀，认为数据已经隔离好了
  failure: 隔离只覆盖了「分数」，没覆盖「过程」。分数能复算，但「它当时为什么这么写」只存在于生成代码里 —— 覆盖后无法判断失败是模型逻辑问题还是环境问题。
  duration: 第二轮跑完即不可逆
  early_signal: 同一批产物里，有的文件带批次后缀、有的不带；或 runs/ 下的文件时间戳全部落在最后一次运行的时间窗内
- attempt: 指望用结果里的 traces 代替留存代码
  failure: traces 里只有 stdout/stderr 的截断片段，看不到完整代码。截图式的日志能证明「发生了什么」，不能证明「它写了什么」，复盘时两者都缺一不可。
  duration: 同理，事后无解
  early_signal: trace 里只存了输出而没存输入（生成代码本身）；或 stderr 被截断到看不见根因
solution: ① 一切「证据类」产物都按批次标识分目录：`runs<tag>/`，与结果文件同生命周期、同一个 tag 变量派生。② 命名里同时带上批次与运行序号，确保任何一份产物都能反查到「哪次实验、哪个模型、哪一组、第几轮」。③
  在清理/自测脚本里显式避开真实产物目录（例如离线自测也走自己的 tag），避免自测把真数据覆盖掉。④ 复盘工具（本次是一个独立的复现驱动脚本）只读原始产物，不写入产物目录。
result: 本项目实际后果：弱模型那一轮的生成代码在事后审计时已被第二轮覆盖，导致「失败是连接层问题还是模型逻辑问题」只能靠 traces 里的 stdout/stderr
  片段间接推断，无法直接读代码确认。修复后代码产物目录按 tag 隔离，同一次审计中的离线自测也不再写入真实产物目录。
retrospective: 「结果隔离了」不等于「证据隔离了」。凡是事后要用来复盘的东西，命名和目录里都必须带得上能区分批次的信息；缺一个维度，一次覆盖就能让整轮实验的「为什么」永久丢失。这条的隐藏成本极高：分数还在，但你已经无法解释它。

## 背景与卡点

同一台机器上先后跑两个模型做交叉验证。结果文件用 AB_TAG 分成了 results.zhipu.json 与 results.deepseek.json，看起来已经隔离好了；但模型生成的代码文件写在共用的 runs/ 目录里，文件名只含「组_任务_第几次_第几轮」，不含模型标识。第二轮跑完后，第一轮的代码被同名文件全部覆盖。等审计时想复盘「第一个模型到底写了什么」，证据已经没有了。
