model: 本地 qwen2.5-coder:7b（Ollama）；Python 3.13 最小环境（仅标准库 + requests，未装 bs4/lxml）；系统提示只写了「requests
  库可用」，没有明确禁止其他第三方库
problem: GBK 解码题（显式坑，对照组 A 用 `re` 模块 5/5 全过）在注入了对应配方之后，处理组 B 变成 **0/5**，整组归零，看起来是「配方把本来会做的题做坏了」。翻出全部
  15 份生成代码（5 次运行 × 最多 3 轮）才发现：**每一份的第一行或第二行都是 `from bs4 import BeautifulSoup`**，而评测环境里没有装
  bs4，于是脚本在 import 阶段就抛 `ModuleNotFoundError`，stdout 为空、一条都没跑。对照组 A 的 5 份代码没有任何一份用过
  bs4 —— 也就是说，**是注入的配方把模型的实现选择推向了第三方 HTML 解析库**，而后者的缺失与「模型会不会解 GBK 编码」这个被考察的能力毫无关系。更麻烦的是：这类失败在汇总表里只是一行普通的
  FAIL，如果不逐份看代码，它会被当成「配方有害」或「模型能力退化」直接写进结论。
dead_ends:
- attempt: 看到处理组（注入配方）通过率显著低于对照组，直接解释为「配方产生了负迁移 / 配方把模型带坏了」
  failure: 这次的方向刚好相反：失败发生在 import 阶段，代码一行都没执行。配方本身没给错方法，是它把模型的实现选择推到了一个环境里不存在的库上。把这归因为「配方有害」，等于让配方背了环境的锅，而真正该修的是「配方缺少依赖前提声明」和「评测环境契约没有说清」。
  duration: 差点写进对外结论，把 B 组 5 条样本全部误判
  early_signal: 同一题在对照组全过、在注入组全灭（5/5 → 0/5），且 stderr 是 `ModuleNotFoundError` 这类**执行前**错误，而不是逻辑错或超时
- attempt: 把 bs4 装进评测环境，让这些脚本能跑，问题就「解决」了
  failure: 这是把仪表盘上的警示灯拆掉：装上之后，评测环境就不再是「最小环境」，而配方「会诱导模型引入重依赖」这个真实风险被彻底掩盖 —— 而在真正的落地场景里，目标机器有没有
    bs4 是不确定的。被测的不再是模型的编码能力，而是「这台机器恰好装了什么」。
  duration: 会永久掩盖一类真实缺陷
  early_signal: 修法是把依赖装上，而不是把契约写清；改完之后处理组通过率立刻追平对照组
- attempt: 只在汇总层加一列「失败原因分类」，把 ModuleNotFoundError 挑出来单独统计
  failure: 分类能解释，但改不了样本本身：那 5 条已经被记成失败，组间对比的分母里躺着 5 条与能力无关的记录。事后分类只能止损，不能把污染样本还原成有效样本。
  duration: 数据已经脏了，只能标注不能修复
  early_signal: 失败原因分类里出现一个占比虽小但整组归零的类别
solution: ① **评测前把环境契约写成显式白名单**：系统提示里不要只说「requests 可用」，而要写「只允许使用标准库与 requests；禁止 import
  其他第三方库（如 bs4、lxml、pandas）」。这样「引用了不可用依赖」从模糊地带变成明确违规，且对四个组一视同仁，指标才测的是同一件事。② **把依赖可用性做成前置校验**：执行前静态扫一遍代码的
  import 语句，若引入白名单外的模块，直接记为「依赖违规（模型失败）」并在 `detail` 里点名是哪个库，而不是让它以一句 `ModuleNotFoundError`
  混进普通失败里。③ **配方卡必须带依赖前提**：凡是正文里出现第三方库的配方，都要在 frontmatter 的 `model` 或正文首段写明所需依赖，否则它在最小环境里会被照抄成跑不起来的代码
  —— 这与「绝对阈值跨站失效」是同一类「配方缺少适用前提」的毛病，只是这次缺的是依赖前提而不是参数前提。④ **对照检查**：同一题在对照组全过、在注入组全灭时，先怀疑「注入内容改变了什么非能力因素」（依赖、运行时长、输出格式），再怀疑能力差异。⑤
  复现方法：把两组生成代码的 import 行单独 diff 一遍，这类问题一眼就能看出来。
result: 实测：A 组 gbk 5/5（全部使用标准库 `re`），B 组 gbk 0/5 —— 全部 15 份生成代码（5 次运行 × 3 轮）无一例外在第一行
  import bs4，报 `ModuleNotFoundError`，stdout 为空；环境确认未安装 bs4（`import bs4` 直接失败）。经此校正，本地模型
  B 组的「显式坑」通过率从 5/15 的原始读数回正为 10/15，与 A 组持平 —— 也就是说，**该组并无能力退化，那 5 条全是依赖缺口**。
retrospective: 这个坑的可怕之处不在它难查，而在它**伪装成结论**：处理组低于对照组，是一个看起来完全合理的实验发现，很容易顺手写进报告。判据其实很简单
  —— 对照组全过、处理组全灭这种「整组归零」的形状，几乎从来不是能力现象，而是某个非能力因素被处理组改变了。后来总结成一条通用规则：**任何「注入 X 之后反而变差」的结果，第一顺位是去查
  X 到底改变了哪条执行路径上的非能力条件（依赖、超时、格式、资源），而不是接受为效应**。另外这也再次说明，配方库缺「适用前提」这个毛病是系统性的：参数前提（阈值要相对化）和依赖前提（用什么库）其实是同一件事的两个面。

  diff
