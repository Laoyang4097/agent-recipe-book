## 现象

```
加配方前：  npm test → 298 通过 / 0 失败
加 3 条后：  npm test → 295 通过 / 3 失败
              ❌ AC-2 用例1 目标排名 ≤ 2 — 实际第 3 位
```

## 根因链

```
新配方 problem 里写了「抓回来的中文页面」
        ↓
与基线 query「抓回来是乱码」撞车，得分虚高到与老配方并列（86% / 6 分）
        ↓
同分时排序依赖 rebuild 的文件遍历顺序（detector < mojibake，字典序靠前）
        ↓
新配方排到老配方前面
        ↓
基线报红
```

三个环节缺一不可：**措辞撞车**（放大）+ **同分**（前提）+ **无确定性 tie-break**（根因）。

## 处置原则

| 想做的动作 | 对不对 | 原因 |
|---|---|---|
| 改测试期望值 | ❌ | 拆警报器 |
| 调全局打分权重 | ❌ | 单条问题不该动全局 |
| 改那条新配方的措辞 | ✅ 已做 | 修因，且让它更准确 |
| 补确定性 tie-break | ✅ 已做 | 消除隐患本身 |

## 根治：确定性 tie-break

```js
scored.sort((a, b) => {
  const d = effectiveScore(b.raw, b.conf) - effectiveScore(a.raw, a.conf);
  if (d !== 0) return d;
  return String(a.recipe.id ?? "").localeCompare(String(b.recipe.id ?? ""));
});
```

有效分相同时按 id 字典序升序。规则本身不重要，**确定性才重要**——只要不依赖文件遍历顺序，加多少配方都不会静默改写既有排名。

## 加完必须反向验证（这一步最容易被省）

修复 + 新增 6 条断言后跑测试：304/0 全绿。

**但全绿不能证明测试有效。** 于是把 tie-break 临时摘掉再跑一次：

```
❌ 逆序 后 Top5 完全一致
❌ 按 id 降序 后 Top5 完全一致
❌ 前半后半交错 后 Top5 完全一致
总计：301 通过 / 3 失败
```

确认能报警，才恢复。

**「全绿」只说明没破坏现状，「摘掉修复会变红」才说明测试真的在守着。**

另外，6 种置换里只有 3 种报警是**正常的**——另外 3 种（按 id 升序、按标题长度、轮转三分一）恰好没扰动到同分对的相对顺序，本来就不该改变结果。设计置换时要明白哪些会扰动、哪些不会，否则会把「测不出来」误当成「没问题」。

## 一句话

**每次入库都是一次对已有排序的重新洗牌。没有基线等于闭着眼睛洗，没有 tie-break 等于洗完还可能记错牌。**
