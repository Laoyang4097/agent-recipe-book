model: A/B/C/D 四组对照实验；pass 由 stdout 正则统计「出现几个不同的 D-xx」判定，零人工打分，温度锁 0
problem: 限流题（静默坑）上，DeepSeek 的裸模型 5/5 全过，而注入了正确配方的处理组只有 3/5 —— 看起来是「配方的文本注入反而把模型带坏了」。逐条读原始轨迹才发现反了：处理组那
  2 次失败，明细是 `got=0/12 rate429=0`，即「一条 429 都没撞、却一条都没算到」。翻出实物代码后确认，模型其实把 12 条数据全部抓到了，只是把采集容器写成了
  `collected[item] = True` 而不是 `= item`，于是最后打印出来的是 12 个 `True`，stdout 里一个 ID 都没有。抓取能力完全相同，被判分器记为
  0。
dead_ends:
- attempt: 用「stdout 里是否出现 12 个不同的 D-xx」作为 pass 的唯一判据，并直接拿 pass 做组间对比
  failure: 两个实现只差一行：`collected[item] = item` → 打印 D-01…D-12，通过；`collected[item] =
    True` → 打印 12 个 True，判失败。两者的抓取逻辑（退避、读响应头、重试）逐行几乎相同，服务端计数也都显示一次没撞限流。同一份能力，pass
    差出 12 条明细。结论方向因此被反转成「配方有害」。
  duration: 直接造成一次错误结论（已撤回）
  early_signal: 明细里 `got=0/12` 同时 `rate429=0` —— 既没有限流错误、又一条都没算到，指向输出格式而非网络或限流；或 stdout
    里出现 `True` / `False` / `1` 这类非目标记号的重复行
- attempt: 认为「任务提示词已经写了『把 12 个 item 值全部打印到 stdout』，所以模型违反契约就该判失败」，不认为这是测量问题
  failure: 契约确实写了、模型确实违反了 —— 但把「合规」和「能力」塞进同一个布尔值，等于让 pass 同时测量两件事。在组间对比中，格式合规率与组别的交互项混进了效应量，且方向随机：可能虚高，也可能像本例一样把真有改善的一组压低。事后无法用
    p 值把两种语义分开。
  duration: 口径问题，污染全部依赖 pass 的对比
  early_signal: 任务提示词里含明确的输出格式约定，而 pass 只由 stdout 正则计算；且明细里没有任何字段单独记录「格式是否合规」
- attempt: 改用人工读 stdout 判断「这其实算通过吧」来补救
  failure: 人工判分引入主观性，破坏「零人工打分」这一前提（本身就是本实验取信于人的基础），且无法批量复现、无法写进自动化。真正缺的不是判官，而是格式无关的地面真值。
  duration: 一旦开例，全部历史结论的判分口径不再一致
  early_signal: 判分环节开始出现「看起来是对的」「应该是这个意思」这类措辞
solution: ① 一个指标只回答一个问题：把 pass 拆成 `pass`（能力：有没有把 12 条拿到）+ `formatOk`（合规：有没有按契约打印成
  item 值）两个字段，主结论只看 pass，formatOk 当控制变量单独报。② 能力判据优先取服务端地面真值：让靶站在 `/_stats` 里一并返回「本次会话已发放过哪些
  item」，按服务端已发放集合与目标集合比对 —— 完全不经过客户端 stdout，对代码写法免疫。③ 必须看 stdout 时要做语义归一：把「以布尔/计数/长度代替值」的变体识别为「采集成功但输出未按契约」，记
  `pass=true, formatOk=false`，而不是直接判失败。④ 对已有数据做敏感性分析：同一格分别按「严格合规」和「能力等价」两种口径各算一次，若结论方向相反，则该结论不成立、不得对外。
result: 用实物代码复核（`runs/B_ratelimit_2_1.py` 通过 vs `runs/B_ratelimit_3_1.py` 判失败）确认两实现只差一行赋值；且失败实现的打印是
  `print(collected.get(key, key))` —— 兜底分支会打印 key 本身（即 `D-03` 这种），既然输出 12 行全是 `True`、一个
  `D-xx` 都没有，逻辑上反证 12 个 key 全部命中采集集合。判定为测量伪影：DeepSeek 处理组限流题的真实能力为 5/5，而 stdout 口径只记
  3/5。改按靶站计数看，处理组 5/5 全部 `rate429=0`（靠读响应头预算主动放慢，一次没撞限流），裸模型 5/5 虽也抓满但每次都撞 3~6 次限流
  —— 配方的真实增益方向与此前结论相反。
retrospective: 与本库已有的 `recipe-py-ratelimit-silent-headers` 修订是同一类问题的两个维度：那条讲「把 rate429
  塞进 pass 会让 pass 与 pitHit 对同一件事重复计数」；这条讲「把输出格式合规塞进 pass 会让 pass 同时测量能力与合规」。归纳出的规律是可复用的：凡是「多件事共用一个布尔判据」，组间对比就会被污染，且污染方向随机、事后极难察觉；判分器设计的第一原则应当是「每个指标只回答一个问题」。另一个教训：看到「加了辅助信息反而变差」这种反直觉结果时，第一顺位应怀疑测量环节而不是接受为效应
  —— 反直觉的效应量往往对应一个没被拆开的指标。
