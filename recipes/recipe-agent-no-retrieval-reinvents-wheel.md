## 背景

给客户端挂上配方库 MCP 之后，在**挂载之前就已经打开**的另一个会话里问了一个库里早有答案的问题（网页抓取中文乱码）。

那个会话没有任何检索工具可用，于是从零写了一份 `fix_encoding.py`（27KB）和一份《乱码速查手册》（4.7KB）。

事后在主库里检索同一句话：

```
matched: 20
第 1 条 recipe-py-encoding-mojibake  matchPct=100  score=9  confidence=A
```

那条配方的 `solution` 已经覆盖了自造手册五条硬规矩里的三条。

## 为什么会这样

MCP server 在**客户端启动时**加载进工具列表。挂载时刻之后新开的会话才有，之前就开着的会话永远看不到。

Agent 是反应式的——它只会用**当前能看到的**工具。工具不在列表里，它没有任何途径知道外部还有个经验库，于是走它最擅长的默认路径：自己写。

## 两层排查法

| 层 | 问题 | 判据 | 不通过怎么办 |
|---|---|---|---|
| 第一层：加载 | 工具在不在列表里 | 在**目标会话**里调一次检索，看命中数 | 重开会话 / 重启客户端 |
| 第二层：调用 | 模型用不用它 | 会话产物里有没有出现「自己写了一份通用指南」 | 作业里显式加一句「先查库再动手」 |

顺序不能反。跳过第一层直接怪模型，会修错地方。

## 副作用：一个可复用的巡检信号

**Agent 开始自己产出「通用速查手册 / 通用清单 / 通用指南」时，八成是它没查到库。**

这类产物本身就是「检索失败」的信号弹——因为真正查过库的 Agent 会引用具体条目编号，而不是写一份放之四海皆准的通用文档。

把这个信号写进巡检清单，比事后复盘便宜得多。

## 一个容易搞反的判断：不查库 ≠ 白干

事后逐条核对了那个会话产出的 8 个知识点：

| 知识点 | 库里有没有 | 判定 |
|---|---|---|
| 别信 `r.encoding`，拿字节而非 `r.text` | 有（第 1 条配方，100% 命中） | 重复造了 |
| 别硬套「中文站 = GBK」 | 有（同配方 dead_end #2） | 重复造了 |
| 别用 `errors='ignore'/'replace'` 硬吞 | 有（同配方 solution ④） | 重复造了 |
| 检测库把 GBK 中文误判成 cp949 | **没有** | 真增量 |
| Big5 与 GBK 字节结构相同，靠 PUA 区分 | **没有** | 真增量 |
| `gb2312`/`gbk` 一律当 `gb18030` | 只有反面案例，无正面建议 | 部分增量 |
| PowerShell `Add-Type` 被安全策略拦 | **没有** | 真增量 |
| Windows 弹窗要用 ctypes 调 MessageBoxW | **没有** | 真增量 |

**3 条重复、5 条增量。**

所以「没查库」的真实代价是：

1. 通用那 3 条白写了一遍——这部分本来读一条配方就能拿到；
2. 环境专属那 5 条，**如果没有人回头补录，就永远丢了**——它们不在任何公开知识库里，是这个环境独有的。

第 2 点才是致命的。通用知识模型迟早会，环境知识不会。

## 别把「重复率」当成拍脑袋的数字

第一版写这条配方时，我写的是「重复造轮子比例约七成」。

这个数字是估的，不是数的。而库里有一条 `recipe-pj-guess-as-conclusion` 专门讲过：**凡是能被 20 分钟实测出来的数，就不要用「大概」代替**。

后来逐条核对，真实比例是 3/8，不是七成。已改正。

写配方的人也会踩配方里的坑——这正是配方库存在的意义。
